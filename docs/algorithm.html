Computing a(16)–a(22) with a row-by-row search

Paint some cells of an n×n grid so that every unpainted cell is orthogonally adjacent to exactly two painted cells. a(n) is the minimum number of painted cells. Starting from a row-by-row DFS, we moved to a row-by-row DP that prunes with a budget and a lower bound (src/dp.rs) and computed a(16)–a(19), beyond the a(15) listed in the OEIS. Putting the same lower bound into the DFS (src/dfs.rs) made it faster than the DP, and building a striped solution first and then proving it minimal (src/stripes_dfs.rs) took us to a(22). That method is now the default. This page explains how, step by step.

Conjectures

Two conjectures: a formula and the shape of solutions

The computed values and solutions suggest two conjectures. Neither is proven.

Conjecture 1 (formula)

a(n) = ⌈(n+2)² / 3⌉ − 6    (n ≥ 7)
  • Evidence: it matches all 16 values for n = 7–22. Equivalently, from n = 8 on the differences are 7, 7, 7, 9, 9, 9, 11, 11, 11, 13, 13, 13, 15, 15, 15: each value repeats three times.
  • Why n²/3: each unpainted cell touches exactly 2 painted cells and each painted cell touches at most 4 cells, so at least a third of the cells must be painted. The (n+2)² form and the −6 presumably come from the edges.

Conjecture 2 (shape of solutions)

For every n ≥ 6 there is an optimal solution in which every row, apart from 2 rows at the top and bottom and 2 columns at the left and right, is a diagonal stripe of period 3 (only columns c ≡ s mod 3 painted, with s depending on the row). The n = 16 figure at the top is an example.

  • Evidence: for n = 6–22, the optimal solution found by the DFS has this shape. This shows such a solution exists for those n; it does not show that every optimal solution is striped.
  • Use: the default algorithm is designed around this conjecture (see "Build from stripes").
Overview

From DFS to DP, and back to DFS

  1. Row-by-row DFS: decide one row at a time from the top. Once two rows are fixed, most of the next row is forced (ideas 1–4). The first version had no lower bound: n = 9 took 16 s and n = 10 did not finish in 2 minutes.
  2. DP (memoization): what can happen below depends only on the last two rows, so paths reaching the same two rows are merged.
  3. Budget and lower bound: decide "can it be done within the budget?" and prune with the minimum number of cells the remaining rows need. This brought a(15) down to a few seconds.
  4. Less memory: keep only two tables. Reconstruct the board with DP passes in alternating directions. Merge left-right mirror states to halve the table.
  5. Lookahead: compute the forced cells of the next row before storing a state, and drop dead ends and over-budget states. 80–90% of the table had been states that die at the next row.
  6. Drop the row above: change the DP state from (row above, current row) to (current row, forced cells below it). Different rows above with the same forced cells lead to the same search.
  7. Back to DFS: putting the budget, the lower bound, the lookahead and the symmetry into the DFS as is made it faster than the DP, with memory for just the n rows of the current path.
  8. Build from stripes, then prove: the interior of optimal solutions is a diagonal stripe pattern of period 3. Build a solution among striped rows first, then prove it minimal by searching every board with one cell fewer. n = 22 went from 552 s to 164 s.
Idea 1

Represent a row as a bit mask and decide rows from the top

Each row is a u64 integer; bit c is 1 when column c is painted. The search is depth-first: starting at the top row, it decides which cells of each row to paint.

The condition on a cell (if unpainted, exactly two painted neighbors) can be checked only once its four neighbors above, left, right and below are all decided. For a cell in row r, that happens when row r+1 is decided.

Idea 2

Once two rows are fixed, most of the next row is forced

Suppose row r and the row r−1 above it are fixed. For an unpainted cell in row r, let s be the number of painted cells above, left and right of it. It then needs 2 − s painted cells directly below. There is only one cell below, so this must be 0 or 1.

So for every unpainted cell in row r, the cell below is determined. Painted cells in row r impose no condition, so only the cells below them are free.

Idea 3

Only the cells below painted cells are free

In the figure, the unpainted cells of row r (yellow band) determine the forced cells of row r+1 (orange). The dashed boxes sit below painted cells of row r; only these may be painted or not.

The candidates for the next row are therefore "forced cells ∪ a subset of the free cells". With k free cells there are 2k candidates, far fewer than the 2n possible rows.

All subsets are enumerated with the bit trick sub = (sub - 1) & cur.

Idea 4

Compute s for a whole row with bit operations

Let a be the row above, b = cur << 1 the left neighbors and c = cur >> 1 the right neighbors. Then, for every bit at once, we can count how many of a, b, c are 1. A bit with s = 1 means "paint below", s = 2 means "do not paint below", and any bit with s = 0 or 3 is a dead end.

pub fn forced_below(full: u64, up: u64, cur: u64) -> Option<u64> {
    let a = up;
    let b = (cur << 1) & full;
    let c = cur >> 1;
    let all3 = a & b & c;
    let ones = (a ^ b ^ c) & !all3;                       // s = 1
    let twos = ((a & b) | (b & c) | (a & c)) & !all3;  // s = 2
    let unpainted = !cur & full;
    if unpainted & !(ones | twos) != 0 {
        return None;                                     // some s is 0 or 3
    }
    Some(unpainted & ones)                               // cells that must be painted below
}
Idea 5 (dfs.rs)

Fix a budget and prune before entering a row

  • Budget: the search asks "can it be done with at most B cells?". B is raised one at a time from a lower bound, and the first feasible B is a(n). How the lower bound is built is explained in "Budget and lower bound" below.
  • Check before entering: for each candidate next row, the forced cells below it are computed first. The search does not enter the row if it is a dead end (a white cell with 0 or 3 painted cells above, left and right), if it is the last row and needs painted cells outside the board, or if "cells painted so far + the minimum the remaining rows need" exceeds the budget.
  • First row and symmetry: the row above the first row is outside the board, so it is treated as 0. A mirrored solution is also a solution, so only first rows no larger than their mirror image are tried.
  • Nodes: the number of times the search enters a row after passing the check, summed over all budgets. This is the same count as the nodes printed by cargo run --release.

Why the first DFS was slow

It solves the same state over and over

What can happen from row k+1 down depends only on rows k−1 and k. Rows further up have already been checked and affect the future only through the number of cells painted so far.

What is unique in the DFS is the path from row 0 to the current row. Many paths share the last two rows and differ only above, and the search below them is identical. The DFS redid that search every time.

  • n = 5, first 3 rows: 1,045 DFS paths but only 357 distinct states.
  • n = 9, first 6 rows: about 670 million DFS paths, but at most 80,000 distinct states at any depth.

This led to the DP, but it later turned out that the main cause was the missing lower bound. The first DFS only checked whether "cells painted so far + forced cells of the next row" reached the best so far, and ignored the cells the remaining rows need. With a lower bound, the search also rarely reaches the same state by different paths (see "Back to DFS").

DP

Use the last two rows as the state and advance row by row, breadth-first

In the first version the state was (row above, current row), and for row k a table mapped each reachable state to the minimum number of cells painted so far. The current dp.rs remembers the forced cells below instead of the row above (see "Merging by forced cells"). The table for row k+1 is built from the table for row k using the forced cells and subsets of the free cells. When the same state is produced more than once, only the smaller count is kept.

The next table depends only on the current one, so two tables, "current row" and "next row", are enough. The DFS remembers only the current path and uses almost no memory; the DP holds every state of a row but removes all duplication.

Budget and lower bound

Prune with the minimum number of cells the remaining rows need

Instead of searching for the minimum directly, fix a budget B and decide "can it be done with at most B cells?". A state is dropped when the cells painted through row k plus the minimum needed by the remaining rows (the lower bound) exceed the budget.

// keep a state whose count through row k is c if
c + anchored[n - 1 - k] <= budget

A single row gives no bound, so use strips

In horizontal stripes "painted row, empty row, painted row", every cell of the empty row has two painted neighbors above and below and is satisfied. So a single row on its own needs 0 cells. However, two empty rows cannot be adjacent, so a strip of several consecutive rows always needs some painted cells.

  • Sh: the minimum for a strip of height h when the rows just outside it may be painted freely. Any solution paints at least this many cells in any h consecutive rows.
  • Bh: the minimum for a strip of height h touching the bottom edge (nothing below it can be painted).
  • Splitting the remaining m rows into one bottom strip plus several free strips and adding their minimums gives a lower bound. The largest over all splits is used.

The strip minimum is computed by a DP that decides the strip one column at a time from left to right. It is the row-wise forcing rotated by 90°, with 4h states (left column, current column). Heights up to h = 9 are used.

The peak of the state count

States peak around the second row from the top

Number of states left in each row's table for n = 16 with budget 102 (measured before the left-right merge).

Bar length is on a log scale.

  • Combinations grow early: the states of row 0 depend only on row 0, at most 2n of them. In rows 1 and 2 they become pairs of rows and grow quickly.
  • Pruning tightens further down: early on, many rows remain and the chained strip bound is loose, so states that painted a little too much survive. As the search goes down, the count accumulates exactly and the bound for the remaining rows becomes accurate.
  • A small rise at the end: "the last row must have no forced cells" can be checked only at the last row, so states that cannot close off at the bottom survive until then.

Even with only two tables, this largest table must be held in memory. It sets the memory limit.

Reconstructing the board

Repeat the DP in alternating directions

With only two tables, the search ends knowing just the minimum and the final state. Everything above has been forgotten. The steps below are those of the first version. The current dp.rs keeps no row above in its states, so it starts from the last row alone and fixes one edge row per DP pass.

  1. Start from the two known bottom rows and run the DP upside down. At the end, the top two rows are fixed.
  2. Start from the known top rows and fix the two rows that connect to the known bottom rows.
  3. Alternate directions until every row is fixed.

Each pass starts from a single fixed state, so the early blow-up of states does not happen. Each pass costs a few percent of the first DP or less, and memory never exceeds that of the first search.

Left-right symmetry

Merge states that are mirror images

A state and its mirror image lead to mirror-image searches with the same minimum. Each new state is compared with its mirror and the smaller one is used as the key. The lower bound is symmetric too, so pruning is unaffected.

If the final state of the search is the mirrored one, mirroring the solution gives a solution ending in that state, so it can be used as the starting point of the reconstruction as is. The reconstruction DP has both ends fixed and is not symmetric, so it does not merge.

Lookahead

Look at the forced cells of the next row before storing a state

When the state (cur, down) for row k+1 is created, only the condition on row cur has been checked. Whether the white cells of row down can be satisfied is known only when the next row is built. Measurements showed that 80–90% of the stored states died at the next row.

  • Do not store dead ends: compute forced_below(cur, down) before storing and skip the state if it is None.
  • Add the forced cells to the bound: the forced cells of the next row will be painted, so a state is also skipped if "count + forced cells + lower bound for the rows after that" exceeds the budget.

Both only drop, one step earlier, states that the next step would drop anyway, so the answer is unchanged.

Merging by forced cells

Remember the forced cells below instead of the row above

The search ahead needs only the current row cur and the cells forced below it, forced. The candidates for the next row are "forced ∪ a subset of the cells below painted cells of cur", and whether that row can be satisfied depends only on cur and the next row. Different rows above with the same forced cells lead to exactly the same search, so the current dp.rs uses (cur, forced) as the state and merges them.

The table is stored as "cur → [(forced, count), …]". For n = 19 with budget 141, the largest table shrank from 6.75 million to 3.05 million states, and the time from 21.5 s to 13.2 s. Without the row above, the board is reconstructed one edge row per DP pass.

The DP demo on this page merges states in the same way.

Back to DFS

With the same pruning, the DFS is faster

The current src/dfs.rs is the DFS with the budget, the strip lower bound, the lookahead and the symmetry added as is. It holds no state table, so it needs memory only for the n rows of the current path. Every n up to 15 finishes within 0.3 s.

  • It stops at the first solution under the feasible budget: the DP builds every row's table even for the feasible budget, which took most of its time.
  • No reconstruction is needed: the current path is the solution.
  • It rarely reaches the same state twice: the lower bound and the lookahead cut paths so much that, even without merging states as the DP does, little work is repeated.

The first DFS was slow not because it was depth-first but because it had no lower bound.

Build from stripes (stripes_dfs.rs)

Build a striped solution first, then prove it minimal

About two thirds of the DFS time went into searching for a solution under the feasible budget. Yet fixing a(n) needs only two facts: a solution with a(n) cells exists, and a(n) − 1 cells are not enough. The first does not have to be found by search; building one is enough. The current default (--algo stripes-dfs) works as follows.

  1. Build a striped solution: as in Conjecture 2, some optimal solution has every row striped with period 3 apart from 2 rows and 2 columns at each edge (checked for n = 6–22). Find the minimum solution among boards restricted to such rows.
  2. Build from the middle: choose the two middle rows among the striped rows (48 kinds) and extend the board row by row toward both edges. Once the two rows are fixed, the upper and lower parts do not interact, so their minimums are found separately and added. Results are memoized by "the two fixed rows and the number of rows to the edge".
  3. Prove it minimal: with U the count of the built solution, an exhaustive DFS with budget U − 1 searches every board. If it finds none, a(n) = U. If it finds one, its count becomes the new U and the step repeats.

The stripe restriction is used only to build a solution, so the conclusion is as rigorous as an unrestricted search.

This method is designed around Conjecture 2 in the "Conjectures" section. If it fails, the answer is still correct: when the striped solution is not minimal, the DFS with budget U − 1 finds a better one and the search keeps descending. In that case, though, the DFS has to search a feasible budget, and the speed advantage is lost.

Not done yet

  1. Parallel proof: the DFS with budget a(n) − 1 is independent for each first-row candidate, so it can scale with the number of cores.
  2. Tighter lower bound: the gap between the bound and the answer is 6–8 for n = 16–19. One unit of budget changes the state count about fourfold, so tightening the bound by 1 is worth roughly one smaller n. Options include taller strips and a bound that depends on the current row.
  3. A cache for the DFS: remember in a fixed-size table that "this state cannot be finished within a remaining budget of A" and skip it when it comes up again. This reduces repeated work for large n while keeping memory fixed.
  4. Proof for general n: prove upper and lower bounds from the "each difference repeats three times" pattern and the diagonal-stripe shape of the solutions.
